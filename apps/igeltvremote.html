Igel TVRemote

A network remote for the smart TVs already on your Wi-Fi, for iPhone, Apple Watch and Mac. Discovery, one pairing per TV, keys, text, wake-on-LAN, 12 App Intents and a macOS MCP server.

macOS · iOS · watchOS Swift 6 · SwiftUI MCP: macOS stdio No release yet

Overview

The app discovers TVs on the current network, pairs once, stores the credential in the Keychain and sends commands directly to the TV. There is no account, no cloud relay and no analytics. Commands travel over the network; there is no infrared emitter and therefore no line-of-sight requirement.

One Swift package holds the protocol adapters, discovery and persistence. The macOS app is a small SwiftUI window; the iOS and watchOS apps are generated from an XcodeGen project. The iPhone relays commands to the watch over WatchConnectivity. A macOS-only MCP helper exposes the saved TVs to agents.

Functional documentation

What you can do

  • Find TVs on the current network, or add one by IP address.
  • Pair once per TV and reconnect automatically, including after a DHCP address change.
  • Send the shared command set: d-pad, OK, back, home, menu, exit, source, info, guide, tools, volume, mute, channel, playback, number pad and colour keys where the platform supports them.
  • Enter text on the TV from the iPhone keyboard for protocols with a text channel.
  • Control the Mac with hardware keyboard shortcuts mapped to remote commands.
  • Wake a TV with Wake-on-LAN when its network interface stays alive in standby and its MAC address is known.
  • On Apple Watch, navigate by tapping or tilting the wrist, change volume with the Digital Crown, and use the keypad and media screens through the paired iPhone.
  • Use Siri and Shortcuts through 12 App Intents, 6 of them registered as shortcuts.
  • Drive the saved TVs from an MCP client on the Mac.

Requirements and permissions

  • macOS 13 or later, iOS 17 or later, watchOS 10 or later; Swift 6 and Xcode 27.
  • Local Network permission on first launch. Without it, discovery returns no results because the platform blocks the socket before a packet leaves the device.
  • iPhone, Mac and watch must be on the same network as the TV. A watch controls through its paired iPhone.

Architecture

  • IgelTVRemoteCore declares macOS 13, iOS 17 and watchOS 10. Its only external dependency is attaswift/BigInt, used by JPAKE.
  • Every non-Samsung platform implements TVRemoteAdapter: connect, disconnect, send, sendText and currentCredential.
  • TVRemoteAdapterFactory maps a TVProtocolID to an adapter. Samsung is the exception: the factory returns nil because Samsung keeps its own WebSocket client.
  • TVRemoteSession is the protocol-agnostic facade used by the iOS and macOS clients for every non-Samsung TV.
  • The UI only sees TVCommand and TVCapabilities; it never learns which protocol is behind a TV.

Discovery

  • SSDP on 239.255.255.250:1900, sent from every broadcast-capable IPv4 interface. Samsung uses urn:samsung.com:device:RemoteControlReceiver:1 with MediaRenderer as a fallback.
  • Bonjour for _amzn-wplay._tcp (Fire TV) and _androidtvremote2._tcp (Android TV).
  • Subnet sweep over the active local subnet with non-blocking port probes, so a dead host does not stall the sweep. This finds TVs on networks that filter multicast.

MultiBrandProbe only accepts private IPv4 addresses. It probes 6466, 43445, 8001, 8060, 3000 and 1925 first; the thorough pass adds 42989, 55000 and 9000, plus port 80 for Sony when enabled. LG on 3000 is accepted only after a real 101 Switching Protocols; Roku and Philips must return a device description.

A saved TV keeps its stable id, name, model, OS, DUID, MACs, last address, pairing identity and per-TV settings. A DHCP change updates the address, not the identity. Legacy tokens stored by IP are migrated when a discovered TV validates the address.

Wake-on-LAN

The magic packet goes to the subnet broadcast address derived from the TV's IP and netmask, using either MAC. The button appears only when a MAC is known. Fire TV exposes no MAC and is woken through ADB. On iOS, Wake-on-LAN is not offered because it needs the multicast/broadcast entitlement.

App Intents and Apple Watch

The iOS target ships 12 App Intents. Each takes an optional TV parameter: a specific saved TV, or the selected one. They go through the same transports as the UI and fail with a message when the TV cannot be reached.

Six are registered as Siri shortcuts with English and Italian phrases: power off/on, mute, volume up/down and playback.

  • The watch sends send_key and send_text messages to the paired iPhone through WatchConnectivity; it never talks to the TV directly.
  • The Digital Crown drives volume through a speed-adaptive leaky bucket.
  • A CoreMotion classifier runs at about 33 Hz, recognises wrist tilt and a fist-clench trigger, and emits haptics at clutch engage/release.
  • The watch UI has a d-pad, keypad/channel screen and media/system screen.

MCP server

Available in source Binary: igeltvremote-mcp Transport: stdio 12 tools

igeltvremote-mcp is macOS-only. It reads the same store.json and Keychain items as the app, speaks JSON-RPC 2.0 over stdio and opens no listening port. The binary ships inside the app bundle at Contents/Helpers/igeltvremote-mcp; running it from the bundle keeps the app's signing identity, Local Network permission and Keychain access.

{
  "mcpServers": {
    "igeltvremote": {
      "command": "/Applications/Igel TVRemote.app/Contents/Helpers/igeltvremote-mcp"
    }
  }
}

Options: --read-only hides/refuses every control tool, --no-power hides power.off, and --self-test runs an in-process handshake for CI. --version and --help are also available.

Limits and security

  • 80 ms minimum between keys per TV, 30 keys per call, 64 steps per sequence; one request at a time per TV.
  • No pairing, app launching or discovery in the MCP server. Pair in the app first; tvs.list shows what is available.
  • stdout is the protocol; logs go to stderr and never contain credentials or payloads. Tokens stay in the Keychain.
  • There is no network listener, so no port to expose and no token to leak.

Build and test

# macOS app + MCP helper
./scripts/package_mac_app.sh
open "dist/Igel TV Remote.app"

# Core, macOS app and MCP tests
(cd IgelTVRemoteCore && swift test)   # 22 tests
(cd IgelTVRemoteMac && swift test)    # 23 app + 27 MCP tests
swift run --package-path IgelTVRemoteMac igeltvremote-mcp --self-test

# Everything, including shell suites and autosign checks
./tests/run_all_tests.sh

# Regenerate iOS/watchOS after editing project.yml
cd IgelTVRemoteiOS && xcodegen generate

Hardware and live-network suites are opt-in with LIVE_SCAN, LIVE_ADB/LIVE_ADB_HOST, LIVE_FIRETV, TLS_TEST_HOST and RUN_SLOW_CRYPTO. CI runs the core and macOS suites, the MCP self-test, and unsigned builds of the iOS/watchOS targets.

Limitations

  • Apple TV is not supported; there is no infrared, so IR-only TVs cannot be controlled.
  • Fire TV is Limited: without developer options and ADB debugging, a current Fire OS device cannot be controlled.
  • On iPhone, raw SSDP needs com.apple.developer.networking.multicast. Until granted, discovery relies on Bonjour and the subnet scan, and Wake-on-LAN is not offered.
  • Roku OS 14.1 requires Settings → System → Advanced system settings → Control by mobile apps to be enabled.
  • A pairing token is tied to the client identity; a build with a different bundle identifier counts as a new client.
  • No release yet. The App Store metadata is being prepared in appStore/.
