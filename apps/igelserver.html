IgelServer

Native Apple clients for a headless Linux server over SSH: telemetry, systemd, Docker, qBittorrent, processes, logs, SMB shares and an encrypted credential vault. macOS and iOS are separate UIs over the same server profile model.

macOS 14+ · iOS 27 Swift 6 · SwiftUI · SwiftPM v2.2.0 · DMG MCP: stdio + HTTP

Overview

IgelServer keeps server profiles on the client and connects to the host you already administer. There is no agent installed on the server and no IgelTools relay. The client platform is Apple-only; the remote host can be any Linux or Unix machine reachable over SSH.

Two clients exist in the repository. The macOS app is a Swift Package Manager executable named ServerPulse (the historical target name) built with SwiftUI and some AppKit integration. The iOS app is a separate Xcode project under ios/, written for iOS 27 with Observation, strict concurrency and Liquid Glass. They share the concepts of a profile and a command set, not a codebase or a database.

Functional documentation

What you can do

  • Profiles. Name, host, port, user, SSH key path or password, optional Tailscale host, route preference, qBittorrent port/user/password/save path. Demo profiles are included and do not touch a real server.
  • Telemetry. Hostname, OS, kernel, CPU model and count, uptime, load average, CPU percentage from /proc/stat deltas, memory and swap, disk mounts, network throughput, active users, failed units and the reboot-required flag.
  • systemd. List services with load/active/sub state, start, stop and restart with sudo, and read journal lines.
  • Docker. List running and stopped containers, start/stop/restart and read the last 100 log lines.
  • qBittorrent. List torrents, add magnet links, URLs or .torrent files, pause, resume and delete with optional file removal.
  • Processes. A live process table with CPU and memory usage; kill by PID after confirmation.
  • Terminal. A command runner with quick commands, a timeout and no full PTY; it can also open the native macOS Terminal with the SSH session.
  • Logs. System journal output with copy and reload.
  • App Hub. A catalog of web interfaces plus user-added apps and containers auto-discovered by exposed web port, opened in the default browser, with an optional localhost mapping.
  • SMB shares. Read the server's smb.conf, mount a share in Finder, eject it and restart Samba.
  • Maintenance. Clean package caches, journal and Docker data on Ubuntu/Debian, or ostree/Flatpak caches on Bazzite; check system updates; check and install app updates.
  • Credentials. A vault for SSH, sudo and service passwords, with biometric or login-password unlock.

macOS window

The sidebar is grouped into monitoring, server control and security. The sections are: Panoramica, App del Server, Servizi Systemd, Container Docker, qBittorrent, Processi, Terminale SSH, Log di Sistema, Manutenzione, Credenziali and Server & Connessione.

iOS app

The iPhone and iPad app is a touch-first client, not a port of the Mac window. Five tabs: Panoramica (telemetry), Server (systemd and Docker), Torrent, Console (command runner) and Impostazioni. It reconnects when the app becomes active and disconnects when it goes to the background.

First run

  1. Edit a profile in Server & Connessione: host, port, user and authentication.
  2. Prefer a key over a password. On macOS the key stays in ~/.ssh; on iOS the key can live in the Secure Enclave and its public half is added to authorized_keys.
  3. Unlock the vault before entering secrets, or let the app prompt for them.
  4. Connect. The host key is accepted on first use and pinned afterwards; a different key aborts the connection.

Limitations

  • There is no Linux, Windows or Steam Deck client in the current tree. The client is Apple-only; the server you connect to can be any Linux or Unix host reachable over SSH.
  • The MCP helper is macOS-only. The iOS app keeps App Intents instead; a stdio or loopback HTTP server cannot run in the iOS sandbox.
  • The terminal is a command runner with a timeout, not an interactive PTY.
  • The macOS vault file is rewritten in place, so an interrupted save can truncate it; keep a backup if the contents matter.
  • macOS and iOS keep separate profiles; there is no profile sync between them.
  • The iOS target requires the iOS 27 SDK and Xcode 27. There is no App Store build; the macOS client is distributed as a DMG.
  • qBittorrent control expects its WebUI on the profile's port, reachable directly or through an SSH-tunnelled curl on the server.

macOS architecture

  • Package.swift declares macOS 14, an executable product ServerPulse and no dependencies.
  • Models: ServerProfile, SystemMetrics, SystemdService, DockerContainer, TorrentItem, ProcessItem, ServerShare, WebServiceApp, CredentialItem.
  • Services: SSHService, MetricsService, QBittorrentService, VaultService, ConfigService, UpdateService, FinderService, NetworkRouteService, AppHubService, CacheStore.
  • State: AppState is the single observable used by the SwiftUI views; it owns the telemetry loop and the selected section.

SSH execution model

  • The macOS client runs /usr/bin/ssh as a child process. It does not link libssh2 and does not implement SSH itself.
  • Options include StrictHostKeyChecking=accept-new, ControlPath=~/.ssh/serverpulse-%C and BatchMode=yes when no password prompt is required. -- terminates option parsing before the destination, so a host or user starting with - cannot inject options.
  • Password authentication uses a generated ~/.ssh/serverpulse_askpass.sh helper, avoiding passwords in process arguments. Sudo passwords go to sudo -S on stdin.
  • The default command timeout is 12 seconds; interactive commands use shorter timeouts. Timeouts terminate the child process and are reported as TIMEOUT.
  • A per-profile queue allows at most 4 concurrent commands per profile and 8 globally. Interactive work outranks telemetry, duplicate in-flight commands are deduplicated, and queued telemetry for the same command is conflated.
  • A circuit breaker opens after 3 consecutive telemetry failures and backs off for 12 seconds, so a sleeping host does not produce a pile of failing SSH processes.

Polling and cache

The telemetry loop changes frequency with the visible section, and service calls are cached with TTLs to avoid re-running expensive remote commands.

Metrics are parsed from /proc/uptime, /proc/stat, /proc/loadavg, /proc/diskstats, /proc/net/dev, free -b, df -h -P, who, systemctl --failed and the /var/run/reboot-required marker. Static specs come from uname, /etc/os-release, nproc and /proc/cpuinfo.

LAN and Tailscale routing

  • A profile can carry a primary LAN host and an optional Tailscale host.
  • RoutePreference is auto, lanOnly or tailscaleOnly. In auto mode the client compares the current IPv4 interfaces with the profile's subnet and picks the LAN address at home, the Tailscale address elsewhere.
  • The resolved route is cached in memory and persisted in UserDefaults so a cold start does not wait for network discovery. NWPathMonitor invalidates the cache when the interface set changes.
  • Every command and web URL uses profile.activeHost, so a route change affects telemetry, SSH, qBittorrent and App Hub together.

qBittorrent transport

The client talks to the qBittorrent Web API at /api/v2. It first tries the active host and port directly, then falls back to curl on the server against 127.0.0.1, which covers a WebUI bound to loopback. Session cookies are kept per host in memory. Pause/resume prefer the qBittorrent 5 stop/start endpoints and fall back to the 4.x pause/resume names.

  • Secrets are stripped from servers.json once the vault is unlocked. If the vault is locked, a password entered during an edit stays in the profile until the next unlock so an unrelated save cannot silently delete it.
  • The vault protects secrets at rest against other local users and casual disk inspection, not against code execution as the same user.
  • Remote output is untrusted. Service and container identifiers are validated before entering a shell command, and SwiftUI renders text without HTML or script execution.
  • Prefer keys over passwords, and Tailscale or WireGuard over exposing SSH and the qBittorrent WebUI to the internet.

iOS specifics

  • iOS cannot launch /usr/bin/ssh. The app speaks SSH in-process with Apple's SwiftNIO SSH and pins host keys with the same TOFU policy.
  • Auth methods are password (Keychain) and Secure Enclave: a P-256 key generated inside the chip, with the private key never leaving it.
  • The UI uses .glassEffect surfaces and system TabView/NavigationStack, with layouts for iPhone, iPad and iPhone Duo postures.
  • RefreshServerIntent is exposed to Siri, Shortcuts and the iOS 27 Siri AI surface; it connects if needed and refreshes telemetry, containers, services and torrents.
  • PrivacyInfo.xcprivacy declares the UserDefaults required-reason API (CA92.1). The Info.plist declares local-network access so SSH and the qBittorrent WebUI are reachable on the LAN.

Build and release

./ci.sh test

# macOS .app + DMG (output: dist/IgelServer-v<version>-<arch>.dmg)
./ci.sh build 2.2.0

./ci.sh test-ios
./ci.sh build-ios

# MCP helper only
./ci.sh test-mcp
./ci.sh build-mcp

# Release to the shared public repository and update the stable feed
./ci.sh release v2.2.0
./ci.sh release-public v2.2.0

Signing and notarization are optional and driven by CODESIGN_IDENTITY and NOTARY_PROFILE. The DMG is the only macOS artifact. Updates read channels/igelserver.json from Chuucommie/IgelTools-Releases first, then fall back to the releases API. The feed publishes macos-aarch64 and macos-x86_64; a DMG without an architecture token is rejected. Before replacing the bundle the installer verifies the code signature with codesign and Gatekeeper with spctl; unsigned updates are refused unless SERVERPULSE_ALLOW_UNSIGNED_UPDATES=1 is set for local development.

Tags are namespaced igelserver-v<version> and the updater ignores releases that do not belong to IgelServer. The source repository is private; artifacts are published in the shared public release repository.

MCP server

Available in source Binary: igelserver-mcp stdio + Streamable HTTP 25 tools

The helper in mcp/ is a native Swift package. It depends only on Foundation and /usr/bin/ssh, reads the same profiles as the macOS app, and ships inside the app bundle at Contents/Helpers/igelserver-mcp. The packaging script signs it with the app so the shared Keychain and SSH identity keep working.

Transports

HTTP mode validates the Origin, MCP-Protocol-Version, Mcp-Method and Mcp-Name headers against the body, rate-limits per IP (default 120/min), returns 202 for notifications and JSON (not SSE) for a single JSON-RPC body. If IGELSERVER_HTTP_TOKEN is unset the server generates one and prints it on stderr. The listener is bound to loopback; it is not a public endpoint.

Shared Keychain

To avoid putting passwords in the MCP client environment, sign the app and the helper with the same Team ID, set the same IGELSERVER_KEYCHAIN_GROUP (for example TEAMID.com.igeltools.igelserver.shared) on both, and enable Accesso MCP in the app's Manutenzione tab. The helper then reads profile.<id>.ssh and profile.<id>.qbit from the shared Keychain. Without the group it falls back to the two environment variables.

Tools by scope

tools/list is filtered by the configured scope, so a read-only client never sees write or destructive tools.

Every tool accepts an optional profile_id unless noted otherwise. The destructive tools require IGELSERVER_SCOPE=destructive and an MCP elicitation/create confirmation before anything runs.

Tasks, resources, prompts and skills

  • Tasks: docker.prune and maintenance.run_upgrade return a task when the client advertises io.modelcontextprotocol/tasks. Poll with tasks/get, cancel with tasks/cancel; tasks persist in mcp-tasks.json.
  • Resources: igelserver://profiles, per-profile telemetry, docker, systemd, torrents and logs/{source}, plus igelserver://docs/security and skill://<name>/SKILL.md.
  • Prompts: diagnose-server, explain-failed-units, capacity-report, security-audit, torrent-triage.
  • Skills: homelab-health, docker-maintenance, torrent-hygiene; list with skills/list, read with skills/get or the resource.

Register it

{
  "mcpServers": {
    "igelserver": {
      "command": "/Applications/IgelServer.app/Contents/Helpers/igelserver-mcp",
      "env": {
        "IGELSERVER_PROFILE": "home",
        "IGELSERVER_SCOPE": "read"
      }
    }
  }
}

For HTTP mode, start igelserver-mcp --http and point the client at http://127.0.0.1:8787/mcp with Authorization: Bearer <token>.

Security and tests

  • Default scope is read; destructive calls require an explicit scope and elicitation. Tool output never contains passwords, tokens or private keys.
  • The audit log records tool, scope, argument hash and outcome, without secrets. SSH uses StrictHostKeyChecking=accept-new and the user's known-hosts; passwords go through an internal SSH_ASKPASS helper, never argv or disk.
  • Container ids, systemd units, torrent hashes, PIDs and signals are validated before use.
  • The package has 21 tests covering parsers, scope, confirmations, tasks, skills and MCP dispatch: (cd mcp && swift test). ./ci.sh test also builds and tests the helper.
