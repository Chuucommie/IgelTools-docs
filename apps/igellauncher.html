IgelLauncher

A single native macOS window that installs, updates and opens the IgelTools suite. Rust and egui, an embedded catalog, SHA-256 verification, receipts and a 13-tool MCP server in the same binary.

macOS only Rust · egui v0.1.0 MCP available

Overview

IgelLauncher is the suite manager, not one of the controlled apps. It reads a small catalog embedded in the binary, detects what is installed, checks each app's GitHub releases, chooses the macOS build for the current CPU, verifies the SHA-256 when one is published and installs the result as an .app bundle in ~/Applications.

The crate compiles only on macOS: main.rs fails the build with compile_error! on any other platform. The app is Rust 2021 with eframe/egui 0.37, no web view and no Electron. The same binary also runs as a stdio MCP server, so the window and an agent share the catalog, release lookup and install code.

Functional documentation

What you can do

  • Browse the suite. Three apps in a card grid or a table ordered by status and then name, with search over name, tagline and description, and a filter for installed apps.
  • See install state. Receipts come first; if there is none, the launcher checks /Applications and ~/Applications for the app's known bundle names and marks the copy as external.
  • Install. Pick a DMG, tar.gz, pkg or ZIP for the Mac's CPU, download it, verify the SHA-256 when one is published and install the .app from a DMG or tar.gz.
  • Update one or all. Compare versions against GitHub releases, update an app, or queue every app with an installable update; jobs show progress and can be cancelled.
  • Open and remove. Open an installed app from the window; uninstall only the copies the launcher installed itself. External copies are left alone.
  • Check the launcher. The launcher checks its own releases too and downloads an update file, verifying it when a checksum is published, but does not replace its running bundle.
  • Work in three languages. English, Italian and German; Automatic follows the system locale and the choice is kept between runs.
  • Read the log. The window shows the current log and can copy it; the file also rotates on launch.
  • Use an agent. igellauncher mcp exposes the catalog, installs, updates, settings and logs over stdio with 13 tools.

First run

  1. Start igellauncher or the installed IgelLauncher.app. It creates its folders and loads default settings; settings.json is written when you save the Settings page.
  2. If the repositories are private, GitHub answers 404 and the app reports No release published yet. Add a token in Settings → GitHub token, or set IGEL_LAUNCHER_TOKEN.
  3. Optionally override the repository for a single app in Settings, or point IGEL_LAUNCHER_MANIFEST at a local JSON feed.
  4. Press Check now (check_on_start is on by default). Install an app; the launcher downloads, verifies and records a receipt.

Pages and layout

  • Library: the suite, search, All/Installed filter and the grid/table switch.
  • Updates: per-app update rows, Update all, and the launcher's own update row.
  • Settings: language, check on start, pre-releases, checksum policy, GitHub token, install folder, repository overrides, and shortcuts to the data folder and log file.
  • Logs: the in-memory tail with a copy button.

Limitations

  • macOS only. There is no Linux or Windows build; the crate refuses to compile elsewhere.
  • Installs are limited to DMG and tar.gz archives that contain an .app bundle. A pkg or ZIP is only downloaded for the macOS installer or Finder.
  • Integrity means SHA-256, not code signing. The launcher does not check Developer ID or notarization before copying a bundle.
  • The GitHub token is stored as plain text in settings.json. Treat that file as a credential store.
  • External copies are detected but not updated or removed, because the launcher does not manage them and does not know their version.
  • Self-update is download-only: the file lands in the updates folder and the user decides how to install it.
  • The embedded catalog descriptions are display strings; they can lag the app pages, which remain authoritative.
  • There is no tray icon and no signed or notarized installer yet. install.sh builds a local .app; the source version is 0.1.0.

Platform and build

  • Rust 1.95+ and the Xcode command line tools. cargo run --release opens the window; cargo test runs 30 tests.
  • install.sh builds the release binary, writes an Info.plist, generates the .icns with sips/iconutil and installs ~/Applications/IgelLauncher.app.
  • The bundle identifier is io.igeltools.launcher; the window app id is io.igeltools.launcher; the plist declares LSMinimumSystemVersion 11.0.
  • The default window is 1120×740, resizable down to 880×560. The icon is the IgelTools brand mark.
  • Only mcp and --mcp are special arguments; everything else starts the window.

Catalog

catalog/suite.json is compiled into the binary with include_str!. It contains the three apps (Igel TVRemote, IgelNotes, IgelServer), the launcher entry, icons and accent colours. For each app the launcher reads:

FieldUse
id, name, tagline, descriptionDisplay, search and MCP output.
repoDefault owner/repo for GitHub releases; overridable per app.
targets, plannedAvailability on the current platform. The launcher only asks about macOS.
mac_bundlesBundle names used for external detection and for finding the .app inside a DMG or tar.gz.
icon, accent, webEmbedded icon, UI accent and the website link.

Availability is computed from targets/planned for macos, so an app marked planned stays planned instead of pretending to exist. The catalog tests assert that every app has a macOS target, a non-empty mac_bundles list and an embedded icon.

Release lookup and versioning

  • GitHub mode calls GET https://api.github.com/repos/<owner>/<repo>/releases?per_page=30 with Accept: application/vnd.github+json, API version 2022-11-28 and user agent IgelLauncher/0.1.0.
  • The token comes from IGEL_LAUNCHER_TOKEN first, then Settings, and is sent as Authorization: Bearer …. It is never returned by MCP.
  • A 404 is treated as “no releases” and logged as a possible private repository. 403/429 rate-limit messages become an explicit error.
  • Drafts are removed. Releases are sorted by a parsed version tag (1.2.3, v2.0.0, 0.4.1-beta.2); prereleases are included only when allow_prereleases is on.
  • IGEL_LAUNCHER_MANIFEST bypasses GitHub entirely and reads a local JSON feed. IGEL_LAUNCHER_DOWNLOAD_BASE rewrites asset URLs to a mirror, keeping only the file name; file:// assets are read from disk.

Asset selection

Only macOS assets are considered. For DMG and pkg, the extension is enough; tar.gz and ZIP must mention macOS in the name (macos, mac, darwin or universal). Assets for another architecture are skipped unless they are universal.

PreferenceKindLauncher installs it?
1.dmgYes: mount, copy the .app, detach.
2.tar.gz / .tgzYes: extract, copy the .app.
3.pkgNo: download only, install with the macOS installer.
4.zipNo: download only, open in Finder.

Architecture tokens match x86_64, x64, amd64, aarch64, arm64 and arm-64. A universal asset matches every Mac. An app with no matching macOS asset shows an error instead of an install button.

Install pipeline

  1. Pick the release (latest stable, optional prerelease, or the exact version requested by MCP) and select the asset for the current CPU.
  2. Resolve the expected SHA-256: the GitHub asset digest (sha256:…), or the line for the asset in a release file named like SHA256SUMS.txt, *.sha256, checksums.txt or sha256.txt.
  3. If no checksum exists and require_checksum is on, refuse the install. The default is on.
  4. Download to the data folder's tmp/ with a 60-second global timeout and a progress callback; cancellation deletes the partial file.
  5. Compute SHA-256. A mismatch deletes the file and aborts.
  6. DMG: hdiutil attach -nobrowse -readonly on a private mount point, find the expected .app, copy it with cp -R, then hdiutil detach.
  7. tar.gz: extract into a scratch folder after rejecting absolute paths and .. traversal, find the expected .app (symlinked directories are not followed), then copy it to the install folder.
  8. Replace an existing bundle at the target path, write the receipt to installed.json, delete the temporary download and log the result.

The install folder is ~/Applications unless install_dir overrides it. The launcher does not run pkg installers and does not unpack ZIP files.

Receipts and update logic

installed.json maps an app id to version, path, kind (dmg or targz), managed and installed_at. A copy found in /Applications or ~/Applications without a receipt is reported as external, managed: false, with no version.

  • A managed app with an installable asset newer than its receipt offers Update; with only a pkg/ZIP newer it offers Download; otherwise it offers Open.
  • An app with no receipt offers Install for DMG/tar.gz, or Download for pkg/ZIP.
  • External copies stay at Installed and are never updated or uninstalled. uninstall_app refuses them explicitly.
  • Update all queues every app with an available update; the queue skips entries whose best asset cannot be installed by the launcher.
  • Version comparison strips a leading v, ignores build metadata, compares numeric components and sorts a prerelease below its release.

Self-update

The launcher checks its own repository with the same release source. Download update writes the selected asset to …/updates/ and verifies its SHA-256 when one is published. It does not enforce require_checksum for this download and does not replace the running bundle; the window shows the path and an Open button. In-place replacement is on the roadmap.

Local release feed

For testing before a repository is published, set IGEL_LAUNCHER_MANIFEST to a JSON file and optionally IGEL_LAUNCHER_DOWNLOAD_BASE to rewrite asset URLs. A macOS entry looks like this:

{
  "apps": {
    "igelserver": {
      "version": "2.2.0",
      "notes": "Local test build",
      "assets": [
        {
          "name": "IgelServer-v2.2.0-aarch64.dmg",
          "url": "file:///absolute/path/IgelServer-v2.2.0-aarch64.dmg",
          "size": 12345678,
          "sha256": "0123…"
        }
      ]
    }
  }
}

sha256 can be omitted only when Refuse installs without a published SHA-256 is off. The manifest also accepts html_url, prerelease and notes.

MCP server

Available in source Binary: igellauncher Args: mcp 13 tools

The launcher binary is also the server. In MCP mode it opens no window: it reads newline-delimited JSON-RPC 2.0 from stdin, writes responses to stdout, and appends operational logs to the rotating log file; only fatal startup errors go to stderr. It advertises protocol 2025-06-18, tools with listChanged: false, empty resources/list and prompts/list, and answers ping.

igellauncher mcp
# or
igellauncher --mcp

Register it with an MCP client

{
  "mcpServers": {
    "igellauncher": {
      "command": "/Users/you/Applications/IgelLauncher.app/Contents/MacOS/igellauncher",
      "args": ["mcp"]
    }
  }
}

When the launcher is built in place, the binary is target/release/igellauncher; after install.sh it lives inside the app bundle. Use the absolute path.

Example

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}

{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
  "name": "check_updates",
  "arguments": {"app_id": "igelserver"}
}}

A successful call returns one text content block with pretty-printed JSON and isError: false. Tool failures keep the JSON-RPC response valid and set isError: true with the message in the text block. A parse error is -32700; an unknown method is -32601.

Known issues and security notes

Read-only annotations are wrong for three tools. In the current source, install_app, update_app and download_app declare readOnlyHint: true even though they write files. An MCP host that gates approval on that hint will not prompt. Treat the server as trusted until the annotations are corrected.

State is loaded at server start. The MCP process loads settings, receipts and external installs once. set_settings writes the file but later calls keep the startup settings; install_app and uninstall_app write receipts but list_installed and open_app keep the startup snapshot. Restart the server to make those changes visible inside the same session.

  • Checksum policy scope. require_checksum is enforced by install_app, update_app and the window's install path. It is not enforced by download_app, the window's download-only action or the launcher's own self-update download; those verify only when a checksum is published.
  • No signature verification. The launcher checks SHA-256, then copies the .app. It does not verify Developer ID or notarization with codesign or spctl.
  • Token on disk. github_token is plain text in settings.json. MCP reports only github_token_set, but the file itself is readable by the user and anything that can read the home folder.
  • Local stdio only. There is no TCP listener. An agent must be able to start the binary as the same user.
  • External installs stay external. The server refuses to uninstall a copy it did not install, even if the bundle name matches an app in the catalog.
  • Download URLs are trusted as published. The checksum decides whether an install proceeds; the launcher does not restrict asset hosts beyond the URL in the release.
