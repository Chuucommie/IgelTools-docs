IgelLauncher

The suite manager: install, update and open the other apps, with the right build for the machine and a verified download. Native Rust and egui.

Linux build runs macOS target Rust · egui MCP available

Overview

IgelLauncher reads a small embedded catalog of the suite, detects what is already installed, checks GitHub releases, and installs the asset that matches the current operating system and CPU. Its own window and its MCP server use the same catalog, release checks and install pipeline.

Functional documentation

What you can do

  • Browse the suite in a card grid or a sortable table, search it, and filter to installed apps.
  • See whether an app is installed, which version, and whether the copy was installed by the launcher or found elsewhere.
  • Install an app, update one, or update all, with progress and cancellation.
  • Open an installed app and remove a launcher-managed copy. External installs are never removed.
  • Check the launcher's own releases, download and verify an update.
  • Read the rotating log inside the window, or copy it.
  • Use the interface in English, Italian or German; Automatic follows the system locale.

First run

  1. Start igellauncher. It creates its data folders and a default settings.json.
  2. If the repositories are private, GitHub answers 404. Set a token in Settings → GitHub token, or override the repository for an app.
  3. Press Check for updates. Apps without a published release stay at No release published yet.
  4. Install an app. The launcher downloads the selected asset, verifies its SHA-256 and records a receipt.

Platform notes

  • Linux. The release build links X11 and runs through XWayland on a Wayland session. AppImages and tar.gz archives are installed; deb/rpm and ZIP assets are offered as downloads for the system package manager.
  • macOS. DMG assets are mounted, the .app is copied to ~/Applications, and the image is detached. The macOS build is the next target; the Linux build is the one that runs today.
  • Windows. The suite does not target Windows yet. MSI/ZIP assets are listed and downloaded but not installed.

Asset selection

Names are matched by extension and architecture token, then ranked per platform:

PlatformPreferenceArchitecture tokens
LinuxAppImage → tar.gz → deb → rpmx86_64, x64, amd64; aarch64, arm64; unity/universal accepted
macOSdmg → tar.gz → pkg → zipSame, plus universal for both CPUs
Windowsmsi → exe → zipSame; download only

Checksums

The expected SHA-256 comes from the GitHub asset digest when present, otherwise from a release asset named like SHA256SUMS.txt, *.sha256, checksums.txt or sha256.txt. The checksum file is parsed, the line for the chosen asset is used, and a mismatch deletes the download.

Default policy. No published checksum means no install, in both the window and MCP. The rule can be turned off in Settings for development builds.

Self-update

The launcher checks its own repository and downloads the matching asset to …/data/updates/, verifying the checksum. It does not replace the running binary: the window says where the file is and asks you to close and reopen the launcher, or to install the file yourself. In-place replacement is on the roadmap.

Local release feed

For testing before a repository is published, set IGEL_LAUNCHER_MANIFEST to a JSON file and optionally IGEL_LAUNCHER_DOWNLOAD_BASE to rewrite asset URLs. A manifest entry looks like this:

{
  "apps": {
    "igelserver": {
      "version": "1.2.3",
      "notes": "Local test build",
      "assets": [
        {
          "name": "igelserver-1.2.3-x86_64.AppImage",
          "url": "file:///absolute/path/igelserver-1.2.3-x86_64.AppImage",
          "size": 12345678,
          "sha256": "0123…"
        }
      ]
    }
  }
}

Architecture

Rust 2021 with eframe/egui. Modules: catalog, release source (GitHub or manifest), platform asset selection, downloader, install/uninstall, receipts and logging, settings, i18n (EN/IT/DE), the egui app and the MCP server. The GUI and MCP share the same primitives; they do not share a process.

Build and test:

cargo run --release          # the window
cargo test                   # 30 tests
./install.sh                 # binary, icon and desktop entry for the current user

MCP server

Available in source Binary: igellauncher Args: mcp

The launcher binary is also the server. It does not open a window in MCP mode; it reads JSON-RPC from stdin, writes responses to stdout and logs to stderr plus the launcher log file.

igellauncher mcp
# or
igellauncher --mcp

Register it with an MCP client

{
  "mcpServers": {
    "igellauncher": {
      "command": "/home/you/.local/bin/igellauncher",
      "args": ["mcp"]
    }
  }
}

Example

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}

{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
  "name": "check_updates",
  "arguments": {"app_id": "igelserver"}
}}

The response is a single text content block containing pretty-printed JSON. Failures set isError: true and keep the protocol response well-formed.

Security rules

  • Local stdio only; no listener. An agent must be able to start the binary as your user.
  • The GitHub token is write-only through MCP; results report only whether it is set.
  • Installs and removals are annotated as non-read-only, so MCP hosts can require approval.
  • The server never bypasses the checksum policy or removes an external install.
  • Download URLs are used as published by the release; the checksum is what decides whether a file is installed.
