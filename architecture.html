Docs / Architecture

Small, local, and honest about state.

The apps share a narrow set of rules: talk to machines the user already owns, keep secrets on the device, publish only what actually builds, and expose a capability to an agent only when a real interface exists.

Principles

  • Local first. TVs are discovered on the LAN; the server is reached over SSH; notes live in a local SwiftData store, optionally synced to an Appwrite instance the user owns. There is no IgelTools relay and no IgelTools account.
  • Native. SwiftUI, SwiftData and AppKit or UIKit on Apple platforms. IgelLauncher is SwiftUI too. No Electron and no web view pretending to be an app.
  • One job per app. The suite grows by addition, not by turning one app into four.
  • Published only when built. A platform is listed as available after it compiles. The same rule applies to MCP: a server is documented as available only when the binary exists.
  • Agents are users too. Every app now exposes an MCP server, with the same limits as the window. Three use stdio on the Mac; IgelNotes uses loopback HTTP inside the app, and IgelServer adds a foreground-only HTTP server on iOS.

Releases and updates

Apps publish through the shared public repository Chuucommie/IgelTools-Releases. Tags are namespaced per app (igeltvremote-vX.Y.Z, igelnotes-vX.Y.Z, igelserver-vX.Y.Z, igellauncher-vX.Y.Z), so one repository can carry several apps without their assets colliding.

Artifact names carry the OS and CPU (macos-aarch64, macos-x86_64), and a release publishes a checksum file or per-asset SHA-256. IgelNotes publishes a DMG with a stable channels/igelnotes.json manifest. IgelServer's public 2.2.0 DMG predates the native macOS/iOS clients, which are still in development. Igel TVRemote has no published release yet; IgelLauncher is at 0.1.0 without a signed installer.

IgelLauncher is the reference client for the generic contract:

  1. Fetch releases for the app's repository (latest stable, or include pre-releases when enabled).
  2. Choose the best asset for this Mac — DMG, tar.gz, pkg or ZIP for macOS. DMG and tar.gz bundles are installed; pkg and ZIP are downloaded for the macOS installer or Finder.
  3. Find the expected SHA-256: the GitHub asset digest, or the matching line in SHA256SUMS.txt / *.sha256.
  4. Download, verify, then install. A mismatch deletes the file and stops.
  5. Record a receipt with version, path and install kind; the window and the MCP server read the same receipts.

No checksum, no install. By default the launcher refuses an asset without a published SHA-256, in the window and in the MCP install/update/download tools. The launcher's own self-update is the exception: it verifies when a checksum exists and does not enforce the policy.

MCP conventions

These rules describe the four servers that exist today. They are not a contract for future apps.

RuleValue
Wire protocolJSON-RPC 2.0, newline-delimited on stdio or JSON over HTTP.
MCP protocol version2025-06-18; IgelServer HTTP also accepts newer protocol headers, IgelNotes accepts older client versions.
Transportsstdin/stdout for IgelLauncher, the IgelServer macOS helper and Igel TVRemote; loopback HTTP for IgelNotes; optional Streamable HTTP for IgelServer's macOS helper; foreground-only HTTP on the local network for IgelServer iOS.
Bindingstdio has no listener. IgelNotes binds 127.0.0.1:8765; IgelServer's macOS helper binds 127.0.0.1:8787; the IgelServer iOS server listens on the local network through Bonjour (_igelserver-mcp._tcp) on port 8788 while the app is in the foreground.
Authstdio relies on the local process. HTTP requires a bearer token; IgelNotes stores it in the Keychain, the IgelServer macOS helper takes IGELSERVER_HTTP_TOKEN or generates one, and the iOS server shows a per-launch token in Settings.
Discoverytools/list returns JSON Schema; resources and prompts are optional. All four expose tools, IgelNotes and IgelServer also expose resources and prompts.
ScopesIgelServer's macOS helper filters tools by read/write/destructive; IgelNotes filters by the same profile names. The IgelServer iOS server exposes a fixed 10-tool set with write annotations. The launcher and TV remote use per-tool hints and flags.
Tool resultsOne text content block with JSON. Tool failures use isError: true; protocol failures use JSON-RPC errors.
AnnotationsreadOnlyHint, destructiveHint, idempotentHint; network tools set openWorldHint where the host supports it.
SecretsNever returned. Tokens and passwords are reported as boolean *_set fields.
Process modelOne local child process per client session, except IgelNotes and the IgelServer iOS server, which live inside the app.

Security model

  • Local surface. stdio servers run as the user; HTTP servers require a bearer token. IgelNotes and the IgelServer macOS helper bind loopback; the IgelServer iOS server is foreground-only and reachable on the local network, with Local Network permission.
  • Same powers as the window. If a tool can restart a service, the window can too. Tools that write are annotated so the host can require approval.
  • Input validation. Identifiers are allowlisted (unit names, container names, torrent hashes, app ids); there is no arbitrary shell tool.
  • Secrets stay in the app. The server reads them where the app already keeps them; tool results never include them.
  • Verification. Launcher installs and downloads require a checksum by default, in both the GUI and MCP; only the launcher's own self-update is verify-when-available.
