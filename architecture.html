Docs / Architecture

Small, local, and honest about state.

The apps share a narrow set of rules: talk to machines the user already owns, keep secrets on the device, publish only what actually builds, and expose a capability to an agent only when a real interface exists.

Principles

  • Local first. TVs are discovered on the LAN; the server is reached over SSH; notes live in a local SwiftData store, optionally synced to an Appwrite instance the user owns. There is no IgelTools relay and no IgelTools account.
  • Native. SwiftUI, SwiftData and AppKit or UIKit on Apple platforms; Rust with egui in IgelLauncher. No web view pretending to be an app.
  • One job per app. The suite grows by addition, not by turning one app into four.
  • Published only when built. A platform is listed as available after it compiles. The same rule applies to MCP: a server is documented as available only when the binary exists.
  • Agents are users too. Where an MCP server exists, it exposes the same capabilities as the window, with the same limits. The launcher has one; the Apple apps do not yet.

Releases and updates

Apps publish through the shared public repository Chuucommie/IgelTools-Releases. Tags are namespaced per app (igelserver-v2.2.0, and the equivalent for the others), so one repository can carry several apps without their assets colliding.

Artifact names carry the OS and CPU (macos-aarch64, macos-x86_64), and a release publishes a checksum file or per-asset SHA-256. IgelServer publishes a DMG only; a DMG without an architecture token is rejected. Its client reads channels/igelserver.json first (version, URL, SHA-256, size) and falls back to the releases API.

IgelLauncher is the reference client for the generic contract:

  1. Fetch releases for the app's repository (latest stable, or include pre-releases when enabled).
  2. Choose the best asset for this Mac — DMG, tar.gz, pkg or ZIP for macOS. DMG and tar.gz bundles are installed; pkg and ZIP are downloaded for the macOS installer or Finder.
  3. Find the expected SHA-256: the GitHub asset digest, or the matching line in SHA256SUMS.txt / *.sha256.
  4. Download, verify, then install. A mismatch deletes the file and stops.
  5. Record a receipt with version, path and install kind; the window and the MCP server read the same receipts.

No checksum, no install. By default the launcher refuses to install an asset without a published SHA-256, in both the window and the MCP install/update tools. The setting can be turned off deliberately; download-only actions verify when a checksum exists but do not enforce the policy.

MCP conventions

These rules are normative for every IgelTools MCP server that exists. Today only IgelLauncher implements a server; the other apps document App Intents or no agent surface at all.

RuleValue
Wire protocolJSON-RPC 2.0 over newline-delimited JSON on stdio.
MCP protocol version2025-06-18; servers answer with the version they implement.
Handshakeinitialize → notifications/initialized. No other notification is required.
Discoverytools/list returns JSON Schema for every tool; resources/list and prompts/list may be empty.
Tool resultsOne text content block containing pretty-printed JSON. Tool failures use isError: true; protocol failures use JSON-RPC errors.
Loggingstderr or the app's log file. Never stdout.
AnnotationsreadOnlyHint for inspection tools, openWorldHint for network operations.
SecretsNever returned. Tokens and passwords are reported as boolean *_set fields.
Process modelLocal child process, one per client session. No TCP listener yet.

Security model

  • Local surface. MCP servers run as the user and only over stdio. An agent must already be able to start a local process to talk to them.
  • Same powers as the window. If a tool can restart a service, the window can too. Tools that write are annotated so the host can require approval.
  • Input validation. Identifiers are allowlisted (unit names, container names, torrent hashes, app ids); there is no arbitrary shell tool.
  • Secrets stay in the app. The server reads them where the app already keeps them; tool results never include them.
  • Verification. Launcher installs require a checksum by default, in both the GUI and MCP.
